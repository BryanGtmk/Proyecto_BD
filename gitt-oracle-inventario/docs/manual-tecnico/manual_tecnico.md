# Manual tecnico

## Arquitectura

El sistema usa Oracle Database como unica base de datos, ASP.NET Core Web API como backend y React + Vite como frontend. La solucion del backend esta separada en Domain, Application, Infrastructure y Api.

## Modelo fisico

El modelo fisico parte del modelo logico y relacional del documento de fase 1. Las tablas principales son ROL, USUARIO, DEPARTAMENTO, UBICACION, CATEGORIA, ARTICULO, PRESTAMO, DETALLE_PRESTAMO, MANTENIMIENTO, MOVIMIENTO, NOTIFICACION y AUDITORIA. El PDF integrador tambien solicita evidencias visuales, por lo que se incorpora la tabla complementaria IMAGEN_ARTICULO asociada a ARTICULO.

## Relaciones

ROL 1:N USUARIO, DEPARTAMENTO 1:N UBICACION, CATEGORIA 1:N ARTICULO, UBICACION 1:N ARTICULO, ARTICULO 1:N IMAGEN_ARTICULO, USUARIO 1:N PRESTAMO, PRESTAMO 1:N DETALLE_PRESTAMO, ARTICULO 1:N DETALLE_PRESTAMO, ARTICULO 1:N MANTENIMIENTO, ARTICULO 1:N MOVIMIENTO, PRESTAMO 1:N NOTIFICACION y USUARIO 1:N AUDITORIA.

## Restricciones

Todas las tablas tienen clave primaria con `GENERATED BY DEFAULT AS IDENTITY`. Se definieron claves foraneas, `NOT NULL`, `UNIQUE` para catalogos y codigos, e indices para correo, codigo, estado, fechas de prestamo y fecha de mantenimiento. Los `CHECK` controlan estados de articulos, tipos de mantenimiento, tipos de movimiento, estados de notificacion y acciones de auditoria.

## Triggers

`TRG_DETALLE_PRESTAMO_VALIDAR` impide que un articulo quede en mas de un prestamo activo. `TRG_ARTICULO_AUDITORIA` registra INSERT, UPDATE y DELETE en ARTICULO. `TRG_DETALLE_PRESTAMO_ESTADO` cambia el estado del articulo a PRESTADO cuando se agrega a un prestamo activo. `TRG_PRESTAMO_DEVOLUCION` devuelve articulos a DISPONIBLE y registra movimiento y auditoria.

## DQL

`database/dql/03_consultas.sql` contiene 14 consultas con JOIN para disponibilidad, categorias, prestamos activos, mantenimientos, movimientos, notificaciones, auditoria, departamentos, historial de prestamos, articulos prestados, usuarios por rol, prestamos vencidos, valor total por departamento y movimientos por rango de fechas.

## Backend

La API usa `Oracle.EntityFrameworkCore`, `GittInventarioDbContext`, JWT, roles y Swagger. Los endpoints principales estan bajo `/api/auth`, `/api/articulos`, `/api/prestamos`, `/api/mantenimientos`, `/api/movimientos`, `/api/reportes`, `/api/usuarios`, `/api/auditoria` y catalogos.

## Frontend

React usa Vite, Tailwind CSS, React Router, Axios y contexto de autenticacion. Las rutas privadas muestran dashboard, inventario, prestamos, devolucion, mantenimientos, movimientos, usuarios, reportes y auditoria.

## Docker

`docker-compose.yml` levanta `oracle-db`, `backend-api` y `frontend-react`. La imagen de Oracle expone 1521 y usa volumen persistente. Si el script no se ejecuta automaticamente, debe correrse manualmente desde SQL Developer o SQL*Plus.

## Ejecucion

1. Copiar `.env.example` a `.env`.
2. Ejecutar `docker compose up --build`.
3. Si Oracle no cargo el script, ejecutar `database/full/00_bd_completa.sql` conectado como `GITT_INV`.
4. Abrir Swagger en `http://localhost:8080/swagger`.
5. Abrir frontend en `http://localhost:5173`.

\subsection{Fundamento teórico del modelo físico, DML y DQL}

El modelo físico de una base de datos representa la implementación concreta del diseño en un sistema gestor, en este caso Oracle. A diferencia del modelo conceptual y del modelo relacional, el modelo físico se centra en la creación real de usuarios, tablas, restricciones, tipos de datos y relaciones que permitirán almacenar la información dentro del sistema.

\subsubsection{Modelo físico de base de datos}

El modelo físico traduce el diseño lógico a una estructura ejecutable. En esta etapa se definen aspectos como nombres de tablas, columnas, tipos de datos, tamaños, restricciones de integridad y vínculos entre entidades. Esta fase resulta importante porque convierte el análisis previo en una base de datos funcional que puede ser creada y utilizada dentro del gestor.

\subsubsection{Claves primarias y claves foráneas}

La clave primaria permite identificar de manera única cada registro dentro de una tabla. Su presencia evita duplicidad y garantiza que cada fila tenga una identidad propia. Por otro lado, la clave foránea establece una relación entre dos tablas, asegurando que los valores ingresados en una tabla dependiente correspondan a registros válidos existentes en la tabla principal.

Estas restricciones son esenciales en el modelo físico porque permiten mantener la integridad referencial y asegurar coherencia entre los datos.

\subsubsection{Lenguaje DDL}

El lenguaje DDL (\textit{Data Definition Language}) se utiliza para definir la estructura de la base de datos. Por medio de instrucciones como \texttt{CREATE USER}, \texttt{CREATE TABLE} y \texttt{ALTER TABLE}, es posible crear los objetos que formarán parte del sistema de almacenamiento.

En el contexto de esta práctica, el DDL permitió construir el esquema físico de cada ejercicio, incluyendo usuarios, tablas y restricciones.

\subsubsection{Lenguaje DML}

El lenguaje DML (\textit{Data Manipulation Language}) permite manipular los datos contenidos en la base de datos. Las instrucciones más comunes son \texttt{INSERT}, \texttt{UPDATE} y \texttt{DELETE}. En esta guía se empleó principalmente \texttt{INSERT INTO} para registrar datos de prueba dentro de las tablas creadas.

El ingreso de datos constituye una fase importante, ya que permite comprobar que las relaciones y restricciones fueron definidas correctamente y que la base de datos puede almacenar información real o simulada de manera consistente.

\subsubsection{Lenguaje DQL}

El lenguaje DQL (\textit{Data Query Language}) está orientado a la recuperación de información. Su instrucción principal es \texttt{SELECT}, la cual permite consultar datos almacenados de acuerdo con distintos criterios. A través de DQL es posible visualizar registros, filtrar información, ordenar resultados y combinar datos de varias tablas.

En esta práctica, las consultas DQL se utilizaron para demostrar que los datos ingresados pueden recuperarse de forma correcta y que la estructura física responde adecuadamente a los requerimientos de información.

\subsubsection{Subconsultas en SQL}

Una subconsulta es una consulta anidada dentro de otra consulta principal. Su función consiste en obtener un resultado intermedio que sirve como criterio para la consulta externa. Las subconsultas permiten formular consultas más expresivas y resolver problemas de recuperación de información que no siempre pueden abordarse con una sola instrucción simple.

En Oracle, las subconsultas resultan útiles para comparar valores, verificar pertenencia, excluir registros y establecer filtros basados en resultados previos. Por ello, su aplicación en esta guía permitió reforzar el análisis de relaciones entre tablas y la interpretación de la información almacenada.

\subsubsection{Integridad de datos}

La integridad de datos hace referencia a la confiabilidad, consistencia y validez de la información guardada en la base de datos. En el modelo físico, esta integridad se mantiene mediante restricciones como \texttt{NOT NULL}, \texttt{PRIMARY KEY}, \texttt{FOREIGN KEY} y \texttt{CHECK}. Gracias a estas restricciones, se evitan registros inválidos, relaciones incoherentes o valores fuera de los rangos esperados.

En consecuencia, la correcta definición del esquema físico, junto con el ingreso adecuado de datos y la posterior consulta de la información, constituye una base importante para lograr un sistema de base de datos estructurado y funcional.

\subsubsection*{Subconsultas en SQL del ejercicio 1}

Las subconsultas son consultas anidadas dentro de otra consulta principal. Se utilizan para obtener datos intermedios que sirven como criterio para la consulta externa. Estas permiten realizar consultas más complejas y precisas sobre la base de datos.

En el ejercicio 1, las subconsultas se aplicaron sobre las tablas \textbf{CLIENTE, PROVEEDOR, PRODUCTO y COMPRA}, con el objetivo de analizar relaciones entre clientes, productos y proveedores.

\subsubsection*{1. Clientes que no han comprado el producto ``Laptop Lenovo''}

Ejemplo del uso de la cláusula NOT IN.

\begin{verbatim}
SELECT NOMBRE, APELLIDOS
FROM CLIENTE
WHERE CI NOT IN (
    SELECT CI_CLIENTE
    FROM COMPRA
    WHERE COD_PRODUCTO = (
        SELECT COD_PRODUCTO
        FROM PRODUCTO
        WHERE NOMBRE = 'Laptop Lenovo'
    )
);
\end{verbatim}

\subsection{Consultas DQL - Subconsultas}

Las subconsultas son consultas anidadas dentro de otra consulta principal. Se utilizan para obtener datos intermedios que sirven como criterio para la consulta externa. Estas permiten realizar consultas más complejas y precisas sobre la base de datos.

En este ejercicio, las subconsultas se aplicaron sobre las tablas \textbf{CLIENTE, PRODUCTO, PROVEEDOR, COMPRA y ENTREGA}, con el objetivo de analizar relaciones entre clientes, productos, proveedores y entregas.

\subsubsection*{1. Clientes que compraron el producto más caro}

Ejemplo del uso de subconsultas anidadas para encontrar el producto con mayor precio.

\begin{lstlisting}[language=SQL, caption={Clientes que compraron el producto más caro}]
SELECT NOMBRE, APELLIDO
FROM CLIENTE
WHERE COD_CLIENTE IN (
    SELECT COD_CLIENTE
    FROM COMPRA
    WHERE COD_PRODUCTO = (
        SELECT COD_PRODUCTO
        FROM PRODUCTO
        WHERE PRECIO = (SELECT MAX(PRECIO) FROM PRODUCTO)
    )
);
\end{lstlisting}

    \centering
    \includegraphics[width=0.5\linewidth]{imagenes/subconsulta1.png}
    \caption{Resultado: Clientes que compraron el producto más caro}

\end{figure}

\textbf{Descripción:} \\
Se identifica el precio máximo de todos los productos, luego se obtiene el código del producto con ese precio, y finalmente se buscan los clientes que compraron dicho producto. En los datos de ejemplo, el producto más caro es el "Monitor 4K" con precio \$1500, comprado por Ana Gomez.

``Una empresa vende productos a sus clientes. Se necesita conocer los datos personales de los clientes (nombre, apellidos, CI, dirección y fecha de nacimiento). Cada producto tiene un código y un nombre, así como un precio unitario y una marca. Un cliente puede comprar varios productos, y un mismo producto puede ser comprado por varios clientes. Los productos son suministrados por diferentes proveedores. Se debe tener en cuenta que un proveedor puede suministrar diferentes productos y que un producto sólo puede ser suministrado por un proveedor. De cada proveedor se conoce el RUC, nombre y dirección.''

\subsubsection{Modelo físico en Oracle del ejercicio adicional 1}
\begin{lstlisting}[language=SQL, caption={Creación de tablas del ejercicio adicional 1}]
CREATE TABLE PROVEEDORES (
    RUC_PROV    VARCHAR2(13) PRIMARY KEY,
    NOM_PROV    VARCHAR2(20) NOT NULL,
    DIR_PROV    VARCHAR2(30) NOT NULL
);

CREATE TABLE CLIENTES (
    CI_CLI      VARCHAR2(10) PRIMARY KEY,
    NOM_CLI     VARCHAR2(15) NOT NULL,
    APE_CLI     VARCHAR2(20) NOT NULL,
    DIR_CLI     VARCHAR2(30) NOT NULL,
    FEC_NAC     DATE NOT NULL
);

CREATE TABLE PRODUCTOS (
    COD_PROD    VARCHAR2(5) PRIMARY KEY,
    NOM_PROD    VARCHAR2(20) NOT NULL,
    PRE_UNIT    NUMBER(8,2) NOT NULL,
    MARCA       VARCHAR2(15) NOT NULL,
    RUC_PROV    VARCHAR2(13) NOT NULL,
    CONSTRAINT FK_PROD_PROV_AD
        FOREIGN KEY (RUC_PROV) REFERENCES PROVEEDORES(RUC_PROV),
    CONSTRAINT CHK_PRE_UNIT
        CHECK (PRE_UNIT > 0)
);

CREATE TABLE COMPRAS (
    ID_COMPRA   NUMBER(5) PRIMARY KEY,
    FEC_COMPRA  DATE NOT NULL,
    CI_CLI      VARCHAR2(10) NOT NULL,
    CONSTRAINT FK_COMP_CLI
        FOREIGN KEY (CI_CLI) REFERENCES CLIENTES(CI_CLI)
);

CREATE TABLE DETALLE_COMPRA (
    ID_COMPRA      NUMBER(5) NOT NULL,
    COD_PROD       VARCHAR2(5) NOT NULL,
    CANTIDAD       NUMBER(5) NOT NULL,
    PRECIO_VENTA   NUMBER(8,2) NOT NULL,
    CONSTRAINT PK_DET_COMPRA
        PRIMARY KEY (ID_COMPRA, COD_PROD),
    CONSTRAINT FK_DET_COMPRA_COMP
        FOREIGN KEY (ID_COMPRA) REFERENCES COMPRAS(ID_COMPRA),
    CONSTRAINT FK_DET_COMPRA_PROD
        FOREIGN KEY (COD_PROD) REFERENCES PRODUCTOS(COD_PROD),
    CONSTRAINT CHK_CANTIDAD
        CHECK (CANTIDAD > 0),
    CONSTRAINT CHK_PRECIO_VENTA
        CHECK (PRECIO_VENTA > 0)
);
\end{lstlisting}

\subsubsection*{13. Ejercicios practicos DQL o subconsultas del ejercicio adicional 1}

Las subconsultas son consultas anidadas dentro de otra consulta principal. Se utilizan para obtener datos intermedios que sirven como criterio para la consulta externa. Estas permiten realizar consultas más complejas y precisas sobre la base de datos.

En el ejercicio adicional 1, las subconsultas se aplicaron sobre las tablas \textbf{CLIENTES, PROVEEDORES, PRODUCTOS, COMPRAS y DETALLE\_COMPRA}, con el objetivo de analizar relaciones entre clientes, productos y proveedores.

\subsubsection*{1. Clientes que no han realizado compras}

Ejemplo del uso de la cláusula NOT IN.

\begin{verbatim}
SELECT NOM_CLI, APE_CLI
FROM CLIENTES
WHERE CI_CLI NOT IN (
    SELECT CI_CLI
    FROM COMPRAS
);
\end{verbatim}

    \caption{Imagen referencial del ejercicio 1 en SQL}
    \label{fig:ad1l1}
\end{figure}

\textbf{Descripción:} \\
Se excluyen los clientes que poseen compras registradas en la tabla ``COMPRAS'', mostrando únicamente aquellos que todavía no han realizado ninguna compra.

\subsubsection*{2. Clientes que compraron productos del mismo proveedor que ``Laptop Lenovo''}

Permite encontrar clientes que compraron productos asociados a un mismo proveedor.

\begin{verbatim}
SELECT NOM_CLI, APE_CLI
FROM CLIENTES
WHERE CI_CLI IN (
    SELECT CI_CLI
    FROM COMPRAS
    WHERE ID_COMPRA IN (
        SELECT ID_COMPRA
        FROM DETALLE_COMPRA
        WHERE COD_PROD IN (
            SELECT COD_PROD
            FROM PRODUCTOS
            WHERE RUC_PROV = (
                SELECT RUC_PROV
                FROM PRODUCTOS
                WHERE NOM_PROD = 'Laptop Lenovo'
            )
        )
    )
);
\end{verbatim}

    \caption{Imagen referencial del ejercicio 2 en SQL}

\end{figure}

\textbf{Descripción:} \\
Primero se identifica el proveedor del producto ``Laptop Lenovo''. Después se localizan los productos de ese mismo proveedor y, finalmente, se muestran los clientes que compraron alguno de esos productos.

Permite identificar productos que todavía no aparecen en ventas registradas.

\subsection{Conclusiones}
El desarrollo de la guía permitió comprender de manera práctica la implementación del modelo físico de una base de datos en Oracle, evidenciando que la creación adecuada de tablas, claves y restricciones constituye la base para el almacenamiento organizado de la información. Asimismo, el ingreso de datos de prueba permitió verificar la validez de las relaciones establecidas y comprobar el funcionamiento de la integridad referencial en los distintos ejercicios.

De igual manera, la ejecución de consultas DQL y subconsultas demostró que una base de datos bien estructurada no solo permite guardar información, sino también recuperarla de forma precisa según diferentes criterios. En consecuencia, la práctica fortaleció la relación entre diseño, implementación y consulta de datos dentro de un entorno real de trabajo con Oracle.

\subsection{Recomendaciones}
Se recomienda verificar cuidadosamente la coherencia entre el modelo relacional y el modelo físico antes de crear las tablas en Oracle, con el fin de evitar errores en claves, nombres de campos o relaciones entre entidades. También es conveniente ingresar datos de prueba que representen distintos escenarios, ya que ello facilita la comprobación del correcto funcionamiento de las restricciones y relaciones definidas.

Además, se recomienda continuar practicando consultas DQL y subconsultas sobre las bases de datos implementadas, puesto que esta fase permite interpretar la información almacenada y validar de manera más completa el trabajo realizado en la construcción del esquema físico.

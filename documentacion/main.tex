\subsection{Fundamento teórico del modelo físico, DML y DQL}

El modelo físico de una base de datos representa la implementación concreta del diseño en un sistema gestor, en este caso Oracle. A diferencia del modelo conceptual y del modelo relacional, el modelo físico se centra en la creación real de usuarios, tablas, restricciones, tipos de datos y relaciones que permitirán almacenar la información dentro del sistema.

\subsubsection{Modelo físico de base de datos}

El modelo físico traduce el diseño lógico a una estructura ejecutable. En esta etapa se definen aspectos como nombres de tablas, columnas, tipos de datos, tamaños, restricciones de integridad y vínculos entre entidades. Esta fase resulta importante porque convierte el análisis previo en una base de datos funcional que puede ser creada y utilizada dentro del gestor.

\subsubsection{Claves primarias y claves foráneas}

La clave primaria permite identificar de manera única cada registro dentro de una tabla. Su presencia evita duplicidad y garantiza que cada fila tenga una identidad propia. Por otro lado, la clave foránea establece una relación entre dos tablas, asegurando que los valores ingresados en una tabla dependiente correspondan a registros válidos existentes en la tabla principal.

Estas restricciones son esenciales en el modelo físico porque permiten mantener la integridad referencial y asegurar coherencia entre los datos.

\subsubsection{Lenguaje DDL}

El lenguaje DDL (\textit{Data Definition Language}) se utiliza para definir la estructura de la base de datos. Por medio de instrucciones como \texttt{CREATE USER}, \texttt{CREATE TABLE} y \texttt{ALTER TABLE}, es posible crear los objetos que formarán parte del sistema de almacenamiento.

En el contexto de esta práctica, el DDL permitió construir el esquema físico de cada ejercicio, incluyendo usuarios, tablas y restricciones.

\subsubsection{Lenguaje DML}

El lenguaje DML (\textit{Data Manipulation Language}) permite manipular los datos contenidos en la base de datos. Las instrucciones más comunes son \texttt{INSERT}, \texttt{UPDATE} y \texttt{DELETE}. En esta guía se empleó principalmente \texttt{INSERT INTO} para registrar datos de prueba dentro de las tablas creadas.

El ingreso de datos constituye una fase importante, ya que permite comprobar que las relaciones y restricciones fueron definidas correctamente y que la base de datos puede almacenar información real o simulada de manera consistente.

\subsubsection{Lenguaje DQL}

El lenguaje DQL (\textit{Data Query Language}) está orientado a la recuperación de información. Su instrucción principal es \texttt{SELECT}, la cual permite consultar datos almacenados de acuerdo con distintos criterios. A través de DQL es posible visualizar registros, filtrar información, ordenar resultados y combinar datos de varias tablas.

En esta práctica, las consultas DQL se utilizaron para demostrar que los datos ingresados pueden recuperarse de forma correcta y que la estructura física responde adecuadamente a los requerimientos de información.

\subsubsection{Subconsultas en SQL}

Una subconsulta es una consulta anidada dentro de otra consulta principal. Su función consiste en obtener un resultado intermedio que sirve como criterio para la consulta externa. Las subconsultas permiten formular consultas más expresivas y resolver problemas de recuperación de información que no siempre pueden abordarse con una sola instrucción simple.

En Oracle, las subconsultas resultan útiles para comparar valores, verificar pertenencia, excluir registros y establecer filtros basados en resultados previos. Por ello, su aplicación en esta guía permitió reforzar el análisis de relaciones entre tablas y la interpretación de la información almacenada.

\subsubsection{Integridad de datos}

La integridad de datos hace referencia a la confiabilidad, consistencia y validez de la información guardada en la base de datos. En el modelo físico, esta integridad se mantiene mediante restricciones como \texttt{NOT NULL}, \texttt{PRIMARY KEY}, \texttt{FOREIGN KEY} y \texttt{CHECK}. Gracias a estas restricciones, se evitan registros inválidos, relaciones incoherentes o valores fuera de los rangos esperados.

En consecuencia, la correcta definición del esquema físico, junto con el ingreso adecuado de datos y la posterior consulta de la información, constituye una base importante para lograr un sistema de base de datos estructurado y funcional.

\subsubsection*{Subconsultas en SQL del ejercicio 1}

Las subconsultas son consultas anidadas dentro de otra consulta principal. Se utilizan para obtener datos intermedios que sirven como criterio para la consulta externa. Estas permiten realizar consultas más complejas y precisas sobre la base de datos.

En el ejercicio 1, las subconsultas se aplicaron sobre las tablas \textbf{CLIENTE, PROVEEDOR, PRODUCTO y COMPRA}, con el objetivo de analizar relaciones entre clientes, productos y proveedores.

\subsubsection*{1. Clientes que no han comprado el producto ``Laptop Lenovo''}

Ejemplo del uso de la cláusula NOT IN.

\begin{verbatim}
SELECT NOMBRE, APELLIDOS
FROM CLIENTE
WHERE CI NOT IN (
    SELECT CI_CLIENTE
    FROM COMPRA
    WHERE COD_PRODUCTO = (
        SELECT COD_PRODUCTO
        FROM PRODUCTO
        WHERE NOMBRE = 'Laptop Lenovo'
    )
);
\end{verbatim}

En la presente base de datos se aplicaron subconsultas sobre las tablas \textbf{PROFESOR, MATERIA, ESTUDIANTES, AULAS y MATRICULA}, con el objetivo de analizar relaciones entre docentes, materias y estudiantes.

\subsection{Ejercicio adicional 1: modelo transaccional de ventas}

\subsubsection*{Enunciado}

``Una empresa vende productos a sus clientes. Se necesita conocer los datos personales de los clientes (nombre, apellidos, CI, dirección y fecha de nacimiento). Cada producto tiene un código y un nombre, así como un precio unitario y una marca. Un cliente puede comprar varios productos, y un mismo producto puede ser comprado por varios clientes. Los productos son suministrados por diferentes proveedores. Se debe tener en cuenta que un proveedor puede suministrar diferentes productos y que un producto sólo puede ser suministrado por un proveedor. De cada proveedor se conoce el RUC, nombre y dirección.''

El desarrollo de la guía permitió comprender de manera práctica la implementación del modelo físico de una base de datos en Oracle, evidenciando que la creación adecuada de tablas, claves y restricciones constituye la base para el almacenamiento organizado de la información.
